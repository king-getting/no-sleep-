# CCUNER 校园小助手 · 项目设计文档

> 校园黑客松参赛项目 | 版本 v0.1 | 2026-10-21

---

## 1. 一句话定位

**专属于华师（CCNU）学生的本地优先 AI 校园助手：数据不出设备，决策过程看得见。**

对标叙事：大厂校园 App 要你的数据、黑盒给你答案；CCUNER 让课表和日程只存在你自己的设备上，并且让你看见多个 AI Agent 是如何协同替你做决定的。

---

## 2. 问题与动机

- 超级课程表 / 今日校园：大而全、不深耕本校；数据上云，隐私无保障；单点问答，没有协同。
- 华师学生真实痛点分散在教务系统、素拓平台、食堂、图书馆等多个孤岛，没有人做整合。
- 现有 AI 助手是黑盒：给一个答案，不知道为什么。

**我们的答案：只做华师 + 本地优先 + 可解释的多智能体编排。**

## 4. 产品范围（MVP，砍到底）

### 4.1 功能一：本校信息汇总（信息 Agent）

- **入口**：首页「今日校园」信息流
- **数据**：mock 三类源——①教务/学院通知 ②讲座与活动 ③生活服务（校车班次、食堂营业、停水停电）。全部走 adapter 接口层，hackathon 后用真实源替换只需改 adapter
- **核心逻辑**：首次使用选身份（本科/研究生/师范生 + 桂子山/南湖校区）并**自设月度餐标**（自行填写、随时可改）；信息流按身份过滤并做相关性打分；每条通知标注「为什么推给我」（依据：年级/校区/培养环节）；餐饮类选项卡标注占今日/本月餐标的比例
- **交互**：卡片流，支持收藏 / 「与我无关」；负反馈本地记录，越用越准
- **不做**：评论、发帖等社交功能

### 4.2 功能二：日程分析（日程 Agent）

- **入口**：「我的这一周」时间轴视图
- **数据**：课表（mock JSON 导入或手动录入）+ 考试 / DDL（手动录入）
- **核心逻辑**：
  - 时间块切分：每天切成「上课 / 整块空档（≥2h）/ 碎片（<45min）」
  - 风险预警：早八连排、午休被课吃掉、DDL 前没有整块复习时间
  - 考试周「生存模式」：DDL 倒计时，把整块空档自动排成复习计划草案
- **交互**：时间轴色块视图，风险项置顶标红；复习计划草案可拖拽调整

### 4.3 功能三：日常建议 = 全天定时报告体系（多 Agent 协同的主场景）

- **形式**：每天三个时段各生成一张报告卡，打开即见，各自侧重不同：
  - **晨间报告（7:30）**：今日概览——课程、空档、风险项（早八 / 连排 / DDL）+ 上午建议
  - **午间报告（11:30）**：上午回顾（上了几节课、碎片时间用得如何）+ 午饭选项卡（见 5.2 示例）+ 下午安排预警 + 小憩建议（健康 Agent）
  - **晚间报告（21:30）**：今日总结——任务完成度、消费回顾（对照餐标预算）+ **明日预告**（早八预警、天气、要带的东西）+ **熬夜提醒**（睡眠 Agent：「现在睡，今晚能睡 7 小时；再刷 1 小时手机，只剩 6 小时」）
- **内容结构**（每张报告）：
  1. 概览区
  2. 建议区——**以选项卡呈现，不替用户决定**（见 4.4）
  3. 每条建议可展开「为什么」（显示各 Agent 的依据）
- **触发**：本地定时 + 手动刷新，全程本地计算，不依赖网络

### 4.4 交互范式：给选项，不替人决定（关键设计）

- 每条建议给出 2–3 张**可执行选项卡**，每张卡标注三要素：**花多少钱 / 花多少时间 / 适不适合现在的你**
- **每张卡附「优势 / 代价 / 可能影响」**（king 补充）：由各 Agent 预测该选项的短期与长期后果，帮助用户做知情选择——选项卡即决策模拟。例：「今晚少睡 1 小时 → 明早前两节课注意力下降风险高」（健康 Agent）、「复习 −1h → DDL 前整块时间不足，需挪用明晚」（日程 Agent）
- 用户点选其一（或忽略），选择结果记录在本地，成为后续建议的偏好输入
- **设计理由**：大学生的决策高度受预算约束，助手替用户拍脑袋（「十点去沁园春」这种脱离真实校园生活的建议）只会被关掉。把选项和成本摆出来、让用户一秒拍板，才是真正的提效——**降解决策成本，而不是替人决策**。

### 4.5 功能四：健康分析（健康 Agent）

- **数据**：睡眠手动录入或模拟穿戴数据；久坐时长由使用记录估算（mock）
- **核心逻辑**：睡眠 × 课表联动——昨晚睡眠 <6h 且今天早八/连排 → 午间报告插入「午间小憩 20 分钟」选项卡；晚间报告生成熬夜提醒；输出一周睡眠/精力趋势
- **交互**：周报卡片 + 选项卡式改善建议（同样只给选项、不给命令）

### 4.6 不服从怎么办（Non-compliance 设计）

设计哲学：**不服从是常态，是信号，不是失败**。产品定位是降低决策成本，执行权永远在用户手里。

- **轻闭环，不追踪**：点选选项卡 = 表达意图；晚间报告回顾时一键标记「做了 / 没做」。不弹通知追问、不搞打卡排名——唠叨是校园 App 卸载率的头号杀手
- **不惩罚**：无红色警告、不重复推送同一条建议、不「教育」用户
- **自动降级而非加码**（核心机制）：同一类建议连续 2–3 次未执行 → 对应 Agent 判定「建议对用户太重」，自动换更轻量版本（「午间小憩 20 分钟」→「闭眼听首歌 10 分钟」）——把坚持失败翻译成建议太重
- **不服从 = 偏好学习**：遵从度写入本地用户画像，成为所有 Agent 后续拆解任务时的输入维度
- **复盘不追责**：晚间报告照实呈现数据（「本周小憩建议 4 次，执行 1 次；平均睡眠 5.8h」），摆事实，不指责
- **编排层反馈环**：不执行信号回流总控编排器，调整后续任务拆解——单点问答式助手做不到的

### 4.7 自设计划未完成怎么办（计划 vs 现实落差）

与 4.6 不同：这是用户**自己定的计划**没执行，涉及自我落差感。设计原则：助手扮演「帮你想办法的人」，不是「记录你失败的人」。

- **只能问，不能侦测**：本地优先下助手无法感知执行结果，由用户在晚间报告中一键确认（「今早你计划吃早餐——吃了吗？」✓ / ✕），10 秒成本，不弹通知追问
- **措辞中性**：不出现「目标未完成」，无红叉；「计划 vs 实际」对照呈现，与建议类未执行共用同一套中性视觉语言
- **问「为什么」，不问「怎么办」**（核心交互）：点「没吃」后给出归因选项（起晚了 / 不饿 / 没时间 / 忘了），归因直接转化为次日建议——选「起晚了」→ 明晨插入「床头备面包 / 便利店选项卡」。用户感知：「它在帮我扫清障碍」，而非「它在记录我的失败」
- **连续未执行 → 提议调小计划**：「每天吃早餐」→「早八日吃早餐」，用最小可行版本保住完成感（行为设计）
- **可关闭**：任何计划追踪一键「不再追问」，关闭即停
- **周报中性呈现**：「本周自设计划完成 5/7」，不评价、不排名

### 4.8 考试周「生存模式」（专题设计）

核心原则：**生存模式改变的是优先级，不放弃底线**——不是通宵引擎。

- **触发与退出**：手动录入考试时间；考前 7 天（可配）自动进入，多场考试各自有冲刺窗口（越近权重越高）；全部结束自动退出并生成「考后小结」

- **模式下系统的变化**：
  1. **报告升级**：三餐报告变为「冲刺报告」——晨间发今日冲刺计划、午间核对进度、晚间复盘完成度并自动重排明日计划（草案始终可拖拽调整）
  2. **Agent 权重动态调整**：日程 Agent 权重提升；信息 Agent 切换过滤模式（讲座/活动推荐暂停，只留考试相关通知）；生活 Agent 反向升级——备考期「按时吃饭」升级为硬提醒且不削减餐标
  3. **复习计划生成规则**：掌握度差的科目优先排整块；记忆类内容插入碎片时间（卡片记忆提示），理解/计算类排整块；每晚复盘后动态重排
  4. **保护机制（呼应 5.3 优先级 2）**：生存模式 ≠ 通宵模式——用户手动把复习排过凌晨 1 点 → 健康 Agent 弹冲突卡而非默默允许；**考前夜「保底睡眠」规则**：建议 23:00 前睡，以选项卡呈现（A 按计划睡 / B 再看 1h，但明早早起复习取消，代价写清）
  5. **考试日模式**：晨间报告切换——物品清单、路线与提前量选项卡

- **考后**：自动退出 + 「考后小结」（计划完成率、平均睡眠、冲突裁决记录）+ 一张放松选项卡（同样只给选项）

- **演示价值**：第二演示场景——同一数据「昨晚睡 5.5h」在平时模式是小憩建议、在考前夜是红线警告，直观展示「上下文感知的动态编排」：Agent 权重随场景切换

- **MVP 裁剪**：手动录入考试 → 倒计时 → 复习计划草案（规则排序）→ 报告切换 + 考前夜冲突卡，足够讲完整故事

### 4.9 首次使用 Onboarding 流程

设计原则：**每步可跳过（身份除外）、全部有默认值、30 秒可完成、随时在设置补录**。

**第 0 屏：隐私承诺前置**。开屏第一句话：「所有数据只存在这台设备上」——最大的信任卖点第一秒建立，而非留到最后。

1. **身份**：本科生 / 研究生 → 年级（大一~大四 / 硕士 / 博士）→ 学院 → 专业（mock 华师学院专业联动下拉）
2. **身体基线**：身高、体重，**知情选填**——标注「不填则健康建议按默认基线计算」，把代价说清楚让用户做知情决定（与「给选项、给影响」的交互哲学一致）
3. **课表导入**：手动录入 / 一键填充示例课表 / 预留教务导入（adapter）；**可跳过，跳过后产品退化为「手动添加日程」模式，报告照常运行**——课表导入是最大流失点，产品不能因没课表而瘫痪
4. **餐标设定**：自设月度餐标 → 自动折算每日参考值
5. **偏好快问快答**（3 题，选项卡形式——onboarding 即交互教学）：作息类型（早起型/夜猫型）、餐饮决策权重（干饭优先/省钱优先/健康优先）、午睡习惯（每天必睡/偶尔/不睡）；答案作为各 Agent 的初始权重
6. **技术性确认**：LLM API Key 选填（不填走本地规则引擎）

**收尾产出「个人画像卡」**：身份、课表、餐标、偏好权重汇总成一张卡供确认回显——既是录入校验，又是产品第一屏，呼应可解释性（用户从一开始就看见系统眼里的自己）。

**示例数据纪律**：示例身份 + 示例课表 + 示例睡眠数据，**带明显的「示例数据」标签，可一键清除退出**——诚实原则：连演示数据都不假装是真的。

**「演示模式」开关**（路演刚需）：一键填充示例数据 + 可手动触发任意时段的报告（模拟 11:30 的午间报告）——路演时间不一定在饭点，定时报告必须能手动唤出。

### 4.10 明确不做（本期）

- 第二课堂学分、选课情报、空教室雷达、失物招领等扩展功能（赛后迭代方向）
- 真实教务系统对接（hackathon 用 mock 数据 + 预留接口）

## 5. 多智能体架构设计

### 5.1 Agent 分工

```
                ┌─────────────────────────┐
                │   总控编排器 (Orchestrator)  │
                │  意图识别 · 任务拆解 · 汇总   │
                └────────────┬────────────┘
        ┌──────────┬─────────┼─────────┬──────────┐
        ▼          ▼         ▼         ▼          
   ┌────────┐┌────────┐┌────────┐┌────────┐
   │教务Agent││生活Agent││健康Agent││日程Agent│
   │课表/考试││食堂/天气││睡眠/精力││碎片时间 │
   └────────┘└────────┘└────────┘└────────┘
        └──────────┴─────────┴─────────┘
                     ▼
              本地数据层 (IndexedDB)
```

- **总控编排器**：接收用户输入或定时触发，拆解为子任务，分派给专职 Agent，汇总结果并生成「建议 + 依据」。
- **专职 Agent**：各自只访问自己域的数据，输出结构化结果（JSON：结论 / 依据 / 置信度）。
- **每个 Agent 的执行过程都记录并可回放**——这是可解释性的实现基础。

### 5.2 可解释输出（每条建议都可展开）

以「午饭建议」为例（11:50 第四节课下课，14:00 才有课）：

```
「午饭吃什么」— 三张选项卡，用户自己选：
├─ 选项 A：一食堂二楼经济窗口（约 ¥8 · 排队 ~5 分钟 · 步行 3 分钟）
│   ├─ 依据（生活 Agent）：该窗口 12:10 前为低峰
│   └─ 依据（财务规则）：符合你本月日均餐标 ¥25 的预算
├─ 选项 B：桂香园轻食（约 ¥15 · 排队 ~15 分钟）
│   └─ 依据（健康 Agent）：你昨晚睡眠 5.5h，清淡饮食午后不犯困
└─ 选项 C：便利店饭团 + 提前去教室（约 ¥10 · 省下 25 分钟）
    └─ 依据（日程 Agent）：下午第一节前有一段碎片时间，可用来预习
用户点选 A / B / C 任一 → 记入本地偏好，影响后续推荐
```

要点：建议**永远附带成本（钱 / 时间）**，且**多选项供选择**——不替用户做决定。

### 5.3 Agent 冲突仲裁机制

**原则：冲突不消灭，显性化；仲裁权归用户；但只把「真冲突」交给用户。**

**L1 可调和冲突 → 总控自动合并**，不打扰用户。

例：午间碎片时间，生活 Agent 说「去取快递」，健康 Agent 说「小憩 20 分钟」→ 总控按空间/时间可行性合并成一条时间线：「先取快递（顺路），回来眯 15 分钟」。

合并规则（优先级从高到低）：

1. 硬约束：上课时间、考试——不可违背
2. 安全红线：连续多日严重缺觉等健康预警——自动升级，覆盖其他建议
3. 用户历史选择（本地偏好画像）
4. 时间/空间可行性（顺路、来得及）
5. Agent 默认权重

**L2 真冲突 → 生成「冲突卡」**，两个方案各挂依据、代价与可能影响，用户二选一。

例：明晚有空档——日程 Agent 排「高数复习 2h」（DDL 预警）；健康 Agent 判定「近三天平均睡 5h，建议提前睡」。

| | 方案 A（学习优先） | 方案 B（健康优先） |
|---|---|---|
| 安排 | 复习至 23:30 | 23:00 睡，明早 7:00 起补 1h |
| 依据 | 日程 Agent：DDL 在 48h 后 | 健康 Agent：睡眠连续不足 |
| 优势 | 复习时间充足，DDL 稳妥 | 睡眠恢复，明早状态好 |
| 代价 | 睡眠连续第 4 天 <6h | 复习时间 −1h |
| 可能影响 | 明早前两节课注意力下降风险高；缺觉累积或影响后天考试状态 | 需挪用明晚 1h 整块时间补复习，压缩休息 |

用户的选择记入偏好：**同类冲突下次默认预填上次的选择**（仍可一键切换）——裁决一次，不再重复打扰。

**产品价值**：单一大模型遇到冲突会 silently 给出折中答案；CCUNER 把两方依据、代价与影响摆出来让用户拍板，并记住拍板模式。周报可呈现「本周自动调和 N 次、你裁决 M 次，你的冲突画像：学习党 / 健康党 / 社交党」。编排动画的最高潮：两个 Agent 打架 → 总控识别为真冲突 → 弹出冲突卡。

### 5.4 模块化契约（接口先行，详见 docs/agent-contract.md）

为了让 2 人并行开发、功能可启停可裁剪，系统全部按**注册式模块**设计：

- **Agent 插件化**：统一 `AgentModule` 接口 + 能力注册表，新增 Agent = 加一个文件 + 注册一行；设置里可按 Agent 单独启停
- **标准件 Schema**：选项卡 / 冲突卡 / 建议均为统一 JSON 结构（含优势 / 代价 / 可能影响 / 依据），UI 只按 Schema 渲染
- **报告 = 区块拼装**：每种报告是一份「配方」（recipe），列明由哪些区块组成——MVP 砍功能 = 改配方，不改代码
- **数据源 adapter 化**：mock 与真实教务源实现同一接口，切换零成本
- **编排事件流**：编排器执行全程发布事件（agent:start / conflict:detected / report:composed），UI 只订阅事件流，**永远不 import 引擎内部**——编排动画与逻辑完全解耦，B 用 mock JSON 即可独立开发
- 完整 TypeScript 契约（A/B 双方的唯一接口）：`docs/agent-contract.md`

## 6. 隐私设计（本地优先）

- 课表、睡眠、日程等个人数据**只存浏览器 IndexedDB，不上传任何服务器**
- AI 推理：Agent 编排逻辑本地运行；如需 LLM，通过用户自填 API Key 调用，密钥仅存本地
- 演示金句：「大厂助手把你的课表存在他们的服务器上，CCUNER 把它存在你的设备上——断网照样用。」

## 14. 项目分工与协同开发（2 人配置）

### 14.1 分工：一人管引擎（逻辑与数据），一人管体验（界面与路演）

| 成员 | 职责 | 关键交付 |
|---|---|---|
| **A · 引擎** | 总控编排器、4 个 Agent 规则引擎、冲突仲裁（§5.3）、偏好与不服从机制（§4.6/4.7）、mock 数据层 + IndexedDB、PWA 离线 | `src/agents/`、`src/data/`、断网演示 |
| **B · 体验** | 三餐报告与选项卡 UI、编排动画、onboarding（§4.9）、视觉落地（§13 品牌）、路演视频与一页介绍 | `src/ui/`、路演素材、在线 Demo 部署 |

（A/B 按各自强项分配，可互换；两边以 `src/agents/` 输出的结构化 JSON 为契约，**接口先行，并行开发**。）

**2 人范围取舍建议**（保演示、砍周边）：

- 保底三件套：午间报告选项卡 + 编排动画 + 断网演示——这三个是评分主体，优先级最高
- 暗色模式简化为「跟随系统的反色版本」，不单独设计
- 信息汇总流做最简卡片版；生存模式只做 §4.8 的 MVP 裁剪版
- 任何想加的新功能，先进 §4.10「明确不做」清单讨论，再决定做不做

### 14.2 协同规范（2 人精简版）

- **接口先行**：第一天先定 Agent 输出结构（结论 / 依据 / 置信度），A 做引擎、B 用 mock JSON 做 UI，互不阻塞
- **分支**：`main` + `feat/*`，PR 合并；时间紧时允许直推 main，但 commit 必须走约定式提交（`feat:` / `fix:` / `docs:` / `chore:`）
- **数据纪律**：mock 数据集中放在 `src/data/mock/`，UI 只通过 adapter 层取数，禁止页面直连假数据
- **演示保护**：演示模式、示例数据相关改动单独提交，随时可回滚
- **同步节奏**：每日两次对齐（午间 + 晚间各 15 分钟），阻塞问题不过夜
